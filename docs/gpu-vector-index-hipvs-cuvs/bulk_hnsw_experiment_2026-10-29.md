# AMD × seekdb：hipVS HNSW 构建加速实验报告

实验日期：2026-10-29。实现提交：`eccc3912f816000e65a75f62d3713e23c486201a`。运行方法见 [构建和复现说明](bulk_hnsw_build.md)。

## 实测结论

最终实现完成两组各 3 轮 CPU / GPU 端到端构建比较。每轮均通过真实 SQL 查询、全量输入向量核对、结果 ID 合法性和本地 Recall@10 ≥ 0.95 检查；GPU 轮次均有完整行数的构建及原生格式导入记录，没有将 CPU 回退计作 GPU 成绩。

| 数据规模 / 维度 | M | CPU 中位数（秒） | GPU 中位数（秒） | 构建加速比 | CPU Recall@10 | GPU Recall@10 范围 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 100,000 / 128 | 32 | 24.137 | 3.798 | **6.355×** | 0.986–0.986 | 0.998–0.999 |
| 500,000 / 128 | 64 | 321.185 | 106.946 | **3.003×** | 0.974–0.974 | 0.989–0.991 |

以上为自建开发数据上的实测结果。赛题尚未给出统一目标倍数、正式数据规模及质量门槛，因此不声称赛事达标、满分或在其他数据分布上有相同加速比。0.95 是本实验自定检查线。算法参数曾在这些开发数据上调优，不把该结果当作独立未知测试集结论。

## 实现范围与来源

基于比赛镜像源码 `de17949d57b9cd2240f141f8116d29bcd495d8d9`，对应上游尚未合并的 [hipVS 参考集成 PR #1314](https://github.com/oceanbase/seekdb/pull/1314)。参考桥接层、镜像库和 Notebook 不作为本作品原创内容；所有新增改动可用 `git diff de17949d57b9cd2240f141f8116d29bcd495d8d9..eccc3912f816000e65a75f62d3713e23c486201a` 审阅。

新增路径在 `CREATE VECTOR INDEX ... lib=cuvs` 的快照输入阶段保存原始 float32 向量和 64 位 ID，独立 worker 使用 hipVS CAGRA 在 AMD GPU 上构图。小于 262,144 行使用 NN-descent 20 次迭代及中间度 4M；更大数据使用 IVF-PQ 候选生成、中间度 8M、refinement rate 4。最终基础图度数不超过 2M。IVF-PQ 仅用于内部候选生成，输出原生 HNSW 保留全部原始 float32 向量，查询精度和 L2 度量保持一致。

CPU 只构建稀疏路由层，并进行连通性检查、格式转换、ID 映射验证和导入；没有先在 CPU 重建全部 HNSW 再遗漏其耗时。独立进程隔离了 hipVS hnswlib 与 VSAG 的 C++ 符号冲突。快照在公布 key 前完成构建，空缓存匹配旧 key 时仍会重载，修复了延迟 GPU 构建暴露的首次查询空结果问题。正常查询、过滤、更新、持久化继续使用 VSAG。

GPU worker 失败会明确报错；不足 256 行或不大于 4M 行的快照显式回退 CPU，未用于性能比较。关闭环境变量或使用 `lib=vsag` 保留 CPU 路径。

## 环境与方法

- AMD Radeon Cloud 模板 3102；设备报告 `AMD Radeon Graphics`，gfx1100、96 CU、49,136 MB 显存；ROCm 7.2.4。未将宿主机全部资源当作容器可用资源。
- 宿主 CPU 为 AMD EPYC 9334；容器 CPU 配额 16，内存上限 55 GiB。两实例都设置 `cpu_count=8`、`memory_limit=16G`、`_memory_budget=16G`、`OMP_NUM_THREADS=8`；CPU 原始镜像二进制与 GPU 候选在同一实例中顺序运行。
- seekdb 1.4.0.0；NumPy 2.4.6、PyMySQL 1.1.2。CPU / 候选 / worker 的 SHA-256 见证据目录。
- 数据由提交的 `make_dataset.py` 生成：PCG64，seed 20261029，128 维 float32，64 个簇，非连续且大于 32 位的文档 ID。100 条查询，K=10；真值对所有原始向量用 float64 L2 穷举计算。两组均无第 K 名距离并列。
- 同一规模 CPU / GPU 的数据、查询、M、ef_construction=200、ef_search=1000 完全相同。导入后逐条在引擎中验证原始 ID 与向量的 L2 距离为零，避免 VECTOR 文本显示舍入造成误判。
- 每轮新表、新索引，不复用预建图；轮次顺序 CPU/GPU、GPU/CPU、CPU/GPU。计时自 CREATE VECTOR INDEX 前开始，至第一条完整有效的 ANN 查询返回为止，包含输入扫描、传输、GPU 同步、转换、导入、持久化及首查触发的工作。
- EXPLAIN 必须含 VECTOR INDEX；每个 GPU 构建须有唯一完整行数的 worker 和 native-ready 记录，native-ready 时间必须在该轮计时区间内。后续 100 条查询分别核对重复/未知 ID、非有限距离、Top-K 完整性和 Recall。
- 数据生成、导入、后续质量校验查询与环境启动不混入构建指标。profiling 和回归测试在正式计时之外进行。不是批量查询加速，也未引用示例 Notebook 的 12.65× 查询成绩。

## GPU 与功能验证

最终 worker 的两条算法路径均另行执行 rocprofv3 kernel / memory-copy trace。100k 捕获 158 条 kernel dispatch、201 条内存复制记录；500k 捕获 14,722 条 kernel dispatch、493 条复制记录。profile 与 SQL 使用同一 worker SHA-256，profile 耗时不计入上表。

9 项 C++/GPU 测试、17 项 Python 验证工具测试通过。GPU 原生格式测试包含非单调 64 位 ID、ID 边界、不可变优化、迭代查询、过滤、序列化/反序列化、后续插入以及失败/空输出 worker 的拒绝。SQL 512 行夹具覆盖负数、零和 64 位主键、过滤、增删改；20 行回退以及空表建索引后首次插入均通过。最终候选自身的 `lib=vsag` 路径也完成同组行为检查。

正式计时结束后，候选实例使用相同数据目录、`HIP_VISIBLE_DEVICES=-1` 且不设置 worker 环境变量重新启动，已通过原生索引持久化、过滤和变更状态检查。该结果证明保存的索引可在无 GPU 构建服务时读取。

## 调试记录及限制

调优早期的 500k / M32 CPU Recall 为 0.937；M64 的 NN-descent、自动选择和初版 IVF-PQ 路径分别出现 0.881、0.902、0.948 的 Recall，均未作为通过结果。早期版本还出现过快照公布与缓存重载竞态导致空结果，以及误用栈上 IVF-PQ 参数导致 worker 析构异常；修复后重新创建索引运行正式全部轮次。前述失败及重试没有混入最终中位数；原始开发记录另行本地归档。

当前实现面向镜像中的 Linux x86_64、gfx1100 和既定 hnswlib 原生格式，支持 dense float32 L2 HNSW、无额外信息列。M 的实现范围为 4–128，实测覆盖 16/32/64。尚未验证其他 GPU、百万级以上、所有 M 值、长期压力或故障注入，不声称生产环境完整认证。较大规模的 refinement 提升了质量，也带来构建开销；本报告同时展示这种代价。
